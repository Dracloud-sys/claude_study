# 02. 사용 기법 — 프롬프트를 넘어 컨텍스트 엔지니어링으로

## 0. 패러다임 정리

| 세대 | 초점 | 한계 |
|---|---|---|
| 프롬프트 엔지니어링 | 문장을 잘 쓰기 | 한 턴짜리. 긴 작업에서 무너짐 |
| **컨텍스트 엔지니어링** | *모델이 보는 창 전체*를 설계 | 현재 표준 |
| 하네스 엔지니어링 | 도구·권한·메모리·평가까지 시스템으로 | 팀/제품 단계 |

컨텍스트 엔지니어링의 4기둥: **지시(instructions) · 검색(retrieval) · 메모리(memory) · 도구(tools)**.

## 1. 컨텍스트 엔지니어링 실전 규칙

### 1-1. 컨텍스트는 예산이다
- 창이 커졌다고 다 채우면 성능이 떨어진다(중간 정보 소실, 주의 분산).
- **관련 없는 파일 10개를 넣는 것보다, 관련 있는 파일 2개 + 그 이유를 넣는 게 낫다.**
- 긴 세션은 정기적으로 압축(`/compact`)하되, **압축 전에 결정사항을 파일로 남긴다**. 요약은 손실이 있고 파일은 손실이 없다.

### 1-2. 지시는 저장소에 커밋한다
- `CLAUDE.md` (프로젝트 루트): 코드 스타일, 금지 사항, 테스트 실행법, 도메인 용어.
  - 짧게 유지 — **매 실행마다 읽히므로 길면 비용이자 노이즈**다.
- 개인 규칙은 `~/.claude/CLAUDE.md`, 디렉터리별 규칙은 하위 `CLAUDE.md`.

### 1-3. 도구 표면을 좁힌다 (MCP tax)
- MCP 서버를 무작정 다 붙이면 도구 스키마만으로 컨텍스트를 수만 토큰 잡아먹고, 모델이 잘못된 도구를 고른다.
- 규칙: **작업에 필요한 커넥터만 켠다.** 자동화(Routine/Action)에서는 특히 최소화.
- 도구 이름·설명은 모델이 읽는 문서다. 애매하면 오호출한다.

### 1-4. 서브에이전트로 컨텍스트를 분리한다
- "코드베이스 전체 탐색" 같은 대량 읽기는 **서브에이전트에 위임**하고 결론만 받는다 → 메인 대화가 가벼워진다.
- 저장소 `.claude/agents/*.md`에 역할별 에이전트 정의(리뷰어, 탐색자, 테스트 작성자).
- 주의: 서브에이전트는 매번 컨텍스트를 새로 쌓으므로 **싸지 않다.** 남발 금지.

### 1-5. 반복 워크플로는 스킬로 자산화한다
- `.claude/skills/<name>/SKILL.md` — "우리 팀의 릴리스 절차", "우리 리뷰 체크리스트" 같은 절차를 재사용 단위로 패키징.
- 스킬은 **버전 관리되고, 리뷰되고, 개선되는 자산**이다. 사람이 매번 프롬프트를 다시 쓰는 것보다 압도적으로 낫다.
- 스킬이 3개 넘어가면 트리거 조건(description)을 정확히 써야 오발동이 없다.

## 2. 에이전트 패턴 카탈로그

| 패턴 | 언제 | 주의점 |
|---|---|---|
| **Plan → Execute** | 변경 범위가 큰 작업 | 계획을 파일로 커밋해야 다른 세션이 이어받음 |
| **Subagent fan-out** | 독립적인 조사·탐색 여러 건 | 결과 통합 비용, 토큰 증가 |
| **Router** | 작업 종류별로 다른 모델/스킬 배분 | 라우팅 규칙 자체가 유지보수 대상 |
| **Review gate** | 생성 → 별도 에이전트가 검증 | 같은 모델의 자기검증은 약함. 관점/역할을 바꿔야 효과 |
| **TDD loop** | 스펙이 명확한 구현 | 테스트를 사람이 먼저 승인해야 의미 있음 |
| **Handoff** | 로컬↔클라우드, 세션↔세션 | 상태를 git/파일로 넘길 것. 대화 요약으로 넘기면 새어나감 |

### 안티패턴
- ❌ 한 세션에서 8시간 몰아 붙이기 → 컨텍스트 오염. 작업 단위로 세션을 끊어라.
- ❌ "알아서 다 해줘" → 성공 기준이 없으면 에이전트는 그럴듯한 데서 멈춘다.
- ❌ 실패한 프롬프트를 계속 다시 던지기 → 실패는 대개 *컨텍스트 부족*이지 *문장 부족*이 아니다.

## 3. RAG / 지식 연결

- **검색은 컨텍스트의 한 입력일 뿐**이다. 코드베이스에선 벡터 검색보다 `grep`/`glob` + 파일 읽기가 더 정확한 경우가 많다.
- RAG가 필요한 곳: 사내 문서, 티켓, 로그처럼 **코드 밖 비정형 지식**.
- 구성 순서: ① 정확한 키워드 검색 → ② 부족하면 임베딩 → ③ 그래도 부족하면 리랭커. 처음부터 3단계를 만들지 말 것.

## 4. 평가(eval) — 이게 진짜 차별점

**자체 eval 없이는 모델도 프롬프트도 스킬도 "개선했다"고 말할 수 없다.**

최소 구성(하루면 만든다):
1. 내 실제 작업 **10건**을 고른다 (해결된 이슈/PR이면 정답이 있어 좋다).
2. 각각에 대해 입력(이슈 본문 + 리포 상태)과 **합격 기준**을 적는다. 기준은 "테스트 통과", "특정 파일이 수정됨"처럼 기계 판정 가능하면 최고.
3. 스크립트로 N회 실행 → 통과율, 평균 토큰, 평균 시간 기록.
4. 모델/프롬프트/스킬을 바꿀 때마다 재실행하고 표에 한 줄 추가.

- 판정이 주관적이면 **LLM-as-judge**를 쓰되, judge 자신을 사람 채점 20건으로 검증한 뒤에 신뢰한다.
- **분산 주의**: 1회 실행 결과로 비교하지 말 것. 최소 3회, 통과율로 본다.

## 5. 안전·보안 기본기

- 에이전트가 읽는 외부 콘텐츠(이슈 본문, 웹페이지, CI 로그, PR 코멘트)는 **전부 신뢰 불가 입력**이다. 프롬프트 인젝션 경로.
- 방어: ① 권한 최소화(쓰기 도구는 꼭 필요한 곳만) ② 네트워크 허용 도메인 제한 ③ 사람 승인 게이트를 되돌리기 어려운 행동(배포, 삭제, 외부 발신) 앞에 둔다.
- 비밀값은 환경변수/시크릿 스토어로. 저장소·프롬프트·로그에 절대 남기지 않는다.
- 자동화가 자기 자신을 트리거하는 루프(봇 코멘트 → 봇 실행 → 봇 코멘트)를 항상 차단한다.
