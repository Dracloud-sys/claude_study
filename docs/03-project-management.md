# 03. AI를 얹은 프로젝트 관리·운용

## 1. 저장소가 곧 에이전트의 운영체제다

AI 에이전트를 도입한다는 건 도구를 하나 사는 게 아니라 **저장소를 에이전트가 읽을 수 있게 재구성**하는 일이다.

```
repo/
├── CLAUDE.md                  # 프로젝트 규칙 (짧게! 매 실행 로드됨)
├── .claude/
│   ├── settings.json          # 권한 허용/거부 규칙, 훅, 환경변수
│   ├── skills/<name>/SKILL.md # 반복 워크플로 (릴리스, 리뷰, 마이그레이션)
│   ├── agents/<name>.md       # 역할 에이전트 (리뷰어, 탐색자)
│   └── hooks/                 # 세션 시작/종료 시 자동 실행 스크립트
├── .mcp.json                  # 프로젝트 스코프 MCP 서버 선언 (팀 공유)
├── docs/plans/                # 계획 문서 (계획→실행 핸드오프의 매개체)
└── .github/workflows/         # CI + 에이전트 자동화
```

**핵심**: 사람이 머릿속에 갖고 있는 암묵지(빌드 방법, 금지 패턴, 리뷰 기준)를
**파일로 내리는 만큼 에이전트의 품질이 올라간다.** 이게 투자 대비 효과가 가장 큰 작업이다.

### CLAUDE.md에 넣을 것 / 뺄 것
| 넣을 것 | 빼야 할 것 |
|---|---|
| 빌드·테스트·린트 실행 명령 | 코드에서 읽으면 되는 아키텍처 서술 |
| 절대 하지 말 것(금지 목록) | 장황한 프로젝트 역사 |
| 도메인 용어 사전 | 자주 바뀌는 TODO |
| 커밋/PR 규칙 | 개인 취향 잔소리 |

## 2. 작업 흐름 — "에이전트는 PR을 만들고, 사람은 머지한다"

```
아이디어/이슈
  ↓  (사람) 스펙과 성공 기준 명시
계획 세션 (plan mode) → docs/plans/xxx.md 커밋
  ↓  (에이전트) 실행 — 로컬 또는 클라우드
브랜치 + PR
  ↓  (에이전트) 자동 리뷰 / CI 자동 수정
  ↓  (사람) 리뷰 · 머지          ← 여기는 절대 자동화하지 않는다
main
```

**불변 규칙 3개**
1. 에이전트는 `main`에 직접 푸시하지 않는다. 전용 브랜치(`claude/...`)만.
2. 머지 승인은 사람이 한다. AI 리뷰는 사람 리뷰의 *보조*이지 대체가 아니다.
3. 되돌리기 어려운 행동(배포, 마이그레이션, 외부 발신, 삭제)은 별도 승인 게이트.

## 3. 작업 분해 — AI에게 주기 좋은 단위

| 좋은 작업 | 나쁜 작업 |
|---|---|
| 성공 기준이 기계 판정 가능 ("이 테스트가 통과") | "코드 품질을 개선해줘" |
| 파일 1~10개 범위 | 리포 전체 리팩터링 한 방 |
| 참고할 유사 선례가 리포 안에 있음 | 전례 없는 아키텍처 결정 |
| 실패해도 브랜치 버리면 끝 | 프로덕션 데이터 조작 |

**요령**: 큰 작업은 사람이 *계획*을 승인하고, 계획의 각 단계를 개별 세션으로 실행한다.
계획서를 커밋해두면 세션이 죽어도, 다른 머신에서도, 클라우드에서도 이어받을 수 있다.

## 4. 리뷰 게이트 설계

3단 방어:
1. **기계적 검증** (CI): 린트, 타입체크, 테스트. 여기서 걸리는 건 사람이 볼 필요 없음.
2. **AI 리뷰**: 코드 리뷰 스킬/Action으로 PR마다 자동 실행. 버그·보안·중복을 인라인 코멘트로.
3. **사람 리뷰**: 설계 적절성, 요구사항 부합, 유지보수성. **여기에 집중할 수 있게 1·2가 잡음을 걷어낸다.**

> AI 리뷰의 함정: 지적이 많다고 좋은 게 아니다. 오탐이 많으면 팀이 전부 무시하게 된다.
> 리뷰 스킬은 **"확신 있는 것만 말하기"** 쪽으로 튜닝하고, 오탐률을 주기적으로 점검한다.

## 5. 관측·비용 관리

- **무엇을 재는가**: 세션당 토큰, 작업당 소요시간, PR 통과율(AI PR 중 사람이 수정 없이 머지한 비율), 롤백률.
- 사용량 대시보드(조직 단위 analytics)로 월 단위 추세를 본다.
- 폭주 방지 장치: `--max-turns`, 워크플로 타임아웃, 동시 실행 제한(concurrency), 예산 알림.
- **PR 통과율이 40% 밑이면** 모델 탓이 아니라 대개 컨텍스트/스펙 탓이다. `CLAUDE.md`와 작업 분해를 먼저 손본다.

## 6. 팀 도입 순서 (실패하지 않는 순서)

1. **1주차 — 읽기 전용**: 코드 설명, 조사, 리뷰 코멘트만. 리스크 0으로 신뢰 쌓기.
2. **2주차 — 저위험 쓰기**: 테스트 추가, 문서, 타입 보강. PR로만.
3. **3주차 — 자산화**: 반복된 프롬프트를 스킬로, 규칙을 `CLAUDE.md`로 내린다.
4. **4주차 — 자동화**: PR 자동 리뷰, CI 실패 자동 수정, 야간 정기 작업.
5. 그 다음: 자체 eval 세트 구축 → 모델/스킬 교체를 데이터로 결정.

**주의**: 4번(자동화)을 1주차에 하면 거의 실패한다. 규칙이 파일로 안 내려간 상태에서 무인 운용하면 산출물이 팀 컨벤션과 어긋나 신뢰를 잃는다.
