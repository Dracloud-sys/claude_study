# 08. GPT ↔ Claude 연동 — API 없이 (0원)

## 전제 교정 2가지

### ① "두 AI를 연동하려면 API가 필요하다" → **아니다**

API는 *자동화* 수단이지 *연동* 수단이 아니다.
두 AI를 연동한다는 건 대화를 파이프로 잇는 게 아니라 **둘이 같은 정본(canon)을 보게 만드는 것**이다.

```
[잘못된 그림]                    [실제로 필요한 그림]
GPT ──API──> Claude              GPT ──┐
(대화를 넘김)                          ├──> 정본 파일 <──┤ Claude
                                       └── 델타(변경분)만 사람이 옮김
```

정본을 양쪽이 알고 있으면, 사람이 옮겨야 할 것은 **"이번에 무엇이 달라졌는가" 한 장**뿐이다.
지금처럼 계획 전문을 통째로 붙여넣는 것보다 **토큰이 훨씬 적게 든다.**

### ② "git을 경유하면 토큰 소모가 크다" → **오해다**

git 자체는 토큰을 **0** 쓴다. 커밋·푸시·diff는 전부 셸 명령이고 모델이 읽는 게 아니다.

비싼 것은 git이 아니라 **에이전트가 저장소를 헤매게 두는 것**이다.

| 실제 비용 | 대략 |
|---|---|
| `git commit` / `push` / `log` | 거의 0 (출력 몇 줄) |
| `git diff`로 변경분만 읽기 | 변경 크기만큼 (보통 수백~수천 토큰) |
| 큰 설정 파일 1개 통째 읽기 | **수만 토큰** ← 여기가 진짜 비용 |
| "알아서 관련 파일 찾아봐" | 수만~수십만 토큰 ← 최악 |

즉 **파일을 지목해서 읽히면 붙여넣기와 비용이 같고, 반복 붙여넣기가 사라지는 만큼 오히려 싸진다.**

## 진짜 토큰이 새는 곳 (현재 구조 기준)

`worldbuilding-innyeok` 스킬의 references 파일 크기:

| 파일 | 크기 | 통째로 읽으면 대략 |
|---|---|---|
| cities.md | 68KB | 2만 토큰대 |
| factions.md | 60KB | 2만 토큰대 |
| architecture.md | 59KB | 2만 토큰대 |
| history-chronology.md | 57KB | 2만 토큰대 |
| combat.md · character-archetypes.md · innyeok.md | 각 ~49KB | 각 1.5만 토큰대 |
| **references 전체** | **~610KB** | **20만 토큰 이상** |

> 한 세션에서 references 3~4개만 읽어도 **git을 100번 쓰는 것보다 비싸다.**
> 절감 레버는 git을 피하는 게 아니라 **아래 3가지**다.

### 절감 조치 (효과 큰 순서)

1. **각 references 파일 맨 위에 "요약 + 목차"를 붙인다**
   ```markdown
   <!-- SUMMARY: 인역의 7대 도시. 각 도시의 영기 밀도, 지배 세력, 계층 구조. -->
   <!-- TOC: §1 영도 §2 하성 §3 ... §7 외곽구 / §8 도시간 관계 -->
   ```
   → Claude가 요약만 읽고 **필요한 섹션만** 추가로 읽게 된다. 2만 → 2천 토큰.

2. **구버전 정본을 references에서 치운다**
   구버전 `innyeok-v2.md`, `v3.md`가 정본과 같은 폴더에 있으면
   에이전트가 v3를 읽으면 **조용히 틀린 설정으로 작업한다.** 일관성 사고의 1순위 원인.
   → `references/archive/`로 이동. 정본 파일명은 개정과 무관하게 `innyeok.md`로 고정한다.

3. **핸드오프 문서에 `touches` 필드를 쓴다** (아래 계약 참고)
   "이번 작업은 factions.md와 cities.md만 건드림" → Claude가 그 둘만 읽는다.

## 방법 1 — 교환 계약(Handoff Contract) ★ 가장 효과 큼

**"연동"의 90%는 API가 아니라 포맷 합의다.**

- GPT 쪽: 커스텀 인스트럭션(또는 Projects 지침)에 **출력 템플릿**을 고정 → `templates/gpt-custom-instructions.md`
- Claude 쪽: 그 템플릿을 읽는 스킬 하나 → `templates/handoff-plan.md` 형식
- 결과: **복붙 1회가 곧 구조화된 작업 지시**가 된다. Claude가 되묻는 왕복이 사라져 토큰이 크게 줄어든다.

| 장점 | 단점 |
|---|---|
| 0원. 오늘 바로 적용 가능 | 처음에 템플릿을 다듬는 품이 든다 |
| 되묻는 왕복 제거 → 토큰 절감 | GPT가 가끔 형식을 어김(→ 지침 상단 고정으로 완화) |
| 사람이 중간 검수 → 창작물 품질에 유리 | 완전 자동은 아님 |
| 어떤 AI로 바꿔도 계약은 그대로 | |

## 방법 2 — 정본을 양쪽에 심기

- Claude: 이미 스킬에 있음 ✅
- GPT: **Projects / 커스텀 GPT의 지식 파일**로 `innyeok.md`(정본) + 자주 쓰는 references 2~3개 업로드
  (업로드 가능 용량·개수는 플랜에 따라 다름. 전부 올리지 말고 **핵심만**)

| 장점 | 단점 |
|---|---|
| GPT에게 세계관을 매번 설명할 필요 없음 | 정본이 바뀌면 **양쪽 다** 갱신해야 함(동기화 부담) |
| 붙여넣는 양이 극적으로 줄어듦 | 플랜에 따라 업로드 제한 |
| GPT의 기획 품질이 올라감(설정 위반 감소) | 구버전이 GPT 쪽에 남아 있으면 오염 |

> 동기화 부담 완화: 정본 갱신은 **월 1회 같은 날**로 고정하고, 그 사이 변경분은 핸드오프 문서로만 흘린다.

## 방법 3 — 로컬 폴더 왕복 (git 없이)

```
project/
  handoff/
    inbox/    ← GPT 답변을 .md로 저장 → Claude에게 "inbox 읽어"
    outbox/   ← Claude 결과 → 필요한 부분만 GPT에 붙여넣기
    archive/
```

| 장점 | 단점 |
|---|---|
| git 학습 없이 즉시 시작 | 이력·되돌리기 없음 |
| 토큰은 지목한 파일만큼만 | 파일이 쌓이면 관리 안 됨 |
| 완전 무료·오프라인 | 여러 기기 간 공유 불가 |

## 방법 4 — git 경유 (작업량이 늘었다면 지금이 적기)

토큰 걱정 없이 쓰는 3규칙:
1. **파일을 지목해서 읽힌다.** "관련 파일 찾아봐" 금지.
2. **전체 재읽기 대신 `git diff`.** "지난 커밋 이후 뭐가 바뀌었는지만 봐."
3. **큰 파일은 요약/목차 먼저.**

| 장점 | 단점 |
|---|---|
| **설정 변경 이력이 남는다** — 창작에선 이게 결정적<br>("이 설정 언제 왜 바꿨지?"에 답할 수 있음) | git 학습 비용 |
| 실수한 설정 변경을 되돌릴 수 있음 | 커밋 규율이 없으면 이점이 사라짐 |
| 여러 기기·클라우드 세션에서 이어받기 가능 | |
| 브랜치로 "가능성 A/B" 병렬 실험 | |

> 창작 IP 작업에서 git의 가치는 코드보다 오히려 크다. 설정 충돌은 **언제 갈라졌는지**를 알면 대부분 풀린다.

## 방법 5 — 역할 분담 고정 (0원, 즉효)

| | GPT | Claude |
|---|---|---|
| 역할 | **발산** | **수렴** |
| 잘하는 일 | 브레인스토밍, 외부 레퍼런스 조사, 초안 다량 생성, 트렌드 감각 | 정본 대조·일관성 검증, 장문 문서화, 코드, 파일 조작, 장시간 작업 |
| 산출 | 아이디어 목록, 기획 초안 | 확정 문서, 에셋 스펙, 실제 파일 |

**둘에게 같은 일을 시키지 않는다.** 지금 하시는 "GPT 계획 → Claude 실행"은 이미 이 원칙에 맞다. 좋은 구조다.

## 방법 6 — Claude 구독 안에서 자동화

Claude Code CLI / 웹 / **Routines(예약 실행)** 는 **구독 사용량**을 쓴다. API 종량 결제를 따로 붙이는 게 아니다.
→ 야간 자동 일관성 검사, 주간 설정 변경 요약 같은 걸 **추가 비용 없이** 돌릴 수 있다. (`docs/05-scheduling.md`)

## 권장 조합

```
1) references에 요약+목차 추가, 구버전 archive로       ← 토큰 절감 최대
2) 핸드오프 계약 템플릿 도입 (templates/)              ← 연동의 실체
3) 정본 핵심만 GPT Projects에 업로드                   ← 붙여넣기 감소
4) handoff/ 폴더로 시작 → 익숙해지면 git으로 승격       ← 이력 확보
5) 익숙해지면 Routines로 야간 일관성 검사 자동화        ← 무인 운용
```

1번만 해도 체감 비용이 가장 크게 떨어진다. **git은 그다음 문제다.**
